# 변경 검토

요청된 검토 범위를 확인한다. 검토만 요청됐다면 실제 코드를 임의로 수정하지 않는다. 수정까지 요청됐다면 확인된 문제를 우선순위에 따라 고치고 검증한다.

## 근거부터 읽는다

- 실제 과제의 필수 조건과 제출 규칙
- 바뀐 파일과 영향을 받는 호출부·입출력
- 작성자가 실행했다고 보고한 검증의 실제 기록

전체 프로젝트를 무조건 재설계하지 않는다. 충분한 근거를 찾은 뒤 필요한 부분으로 범위를 좁힌다.

## 다음을 확인한다

1. 필수 흐름이 실제로 연결되는가?
2. 정답이 틀리는 입력이나 상태가 있는가?
3. 데이터가 누락·중복·조용히 변형되는가?
4. 오류가 사용자에게 성공으로 표시되는가?
5. 비밀값·개인정보·과제 데이터가 불필요하게 노출되는가?
6. 요구에 없는 복잡한 구조나 외부 의존이 시간을 소모하는가?
7. 문서·코드·실행 기록·설명이 서로 맞는가?

## 지적을 행동으로 연결한다

각 지적에 중요도, 파일·함수 또는 실행 근거, 재현 조건, 실제 영향, 최소 수정 방향, 확인 방법을 붙인다. 추정은 추정으로 표시한다. 막연한 일반론과 근거 없는 보안 경고를 늘어놓지 않는다.

중요도는 제출/실행 차단, 결과 오류·필수 누락, 영향이 제한된 문제, 선택 개선으로 구분한다. 문제가 없으면 확인한 범위와 잔여 한계를 말한다. 검토 통과를 공식 채점 통과로 표현하지 않는다.
