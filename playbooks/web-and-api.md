# 화면·서버·API 과제

API는 프로그램끼리 입력과 결과를 주고받는 약속입니다. 화면이 만들어진 상태, 서버가 응답한 상태, 사용자의 일이 끝난 상태를 각각 확인합니다.

## 1. 사용자 흐름 하나부터 연결

예시: 입력 → 유효성 확인 → 서버 요청 → 처리 → 결과 표시 → 사용자의 다음 행동.

처음에는 한 가지 정상 사례를 끝까지 연결합니다. 각 화면을 따로 꾸미기 전에 실제 데이터가 전체 흐름을 통과하는지 확인합니다.

## 2. 입력과 출력 약속

| 정할 내용 | 예시 질문 |
|---|---|
| 입력 필드 | 무엇이 필수이고 어떤 형식이어야 하나요? |
| 범위 | 음수·빈값·지나치게 큰 값은 허용하나요? |
| 결과 형식 | 어떤 필드와 단위가 반환되나요? |
| 오류 | 사용자가 수정할 입력 오류와 내부 실패를 어떻게 구분하나요? |
| 중복 요청 | 같은 버튼을 두 번 누르면 어떤 결과가 되나요? |
| 저장 | 새로고침·재실행 후 데이터가 남아야 하나요? |

이미 제공된 API나 프로젝트 구조가 있다면 그 약속을 먼저 따릅니다. 출력 필드명을 바꾸는 작은 수정도 다른 기능을 깨뜨릴 수 있습니다.

## 3. 화면에서 확인할 상태

- 시작 상태: 무엇을 해야 하는지 알 수 있음
- 입력 오류: 고칠 항목과 이유를 알 수 있음
- 처리 중: 중복 실행 여부를 제어하고 진행 상태를 알림
- 성공: 결과와 다음 행동을 알 수 있음
- 결과 없음: 정상적으로 비어 있는 상황임을 설명
- 실패: 성공처럼 표시하지 않고 재시도 가능 여부를 알림

실제 화면 확인은 시험이 허용하는 내장 브라우저와 조작 방식으로 수행합니다. 이 안내는 브라우저 자동화나 Computer Use 사용을 허용하는 근거가 아닙니다.

## 4. 서버·처리 코드 확인

- 예상하지 못한 입력이 내부 오류로 이어지지 않는지 확인합니다.
- 사용자에게 표시되는 오류에 키·토큰·내부 민감정보가 포함되지 않게 합니다.
- 경로·파일명 입력이 있다면 의도한 작업 범위를 벗어나지 않게 검증합니다.
- 외부 호출이 필요한 과제라면 허용된 연결만 사용하고 실패·지연을 처리합니다.
- 저장이 필요한 과제라면 저장 성공과 화면 성공 표시를 연결합니다.
- 인증·분산 구조·복잡한 저장소는 과제에 필요한 이유부터 판단합니다.

## 5. 검증할 사용자 흐름

| 사례 | 확인할 것 |
|---|---|
| 정상 입력 | 올바른 결과까지 이어짐 |
| 필수 입력 누락 | 수정할 위치와 이유가 표시됨 |
| 처리 실패 | 실패를 알려주고 잘못된 성공 결과를 남기지 않음 |
| 같은 입력 반복 | 의도한 중복 처리 정책을 따름 |
| 상태 변경 | 표·요약·버튼 상태가 일관됨 |
| 다시 실행 | 문서의 실행 방법으로 핵심 흐름 재현 가능 |

모든 시스템에 모든 사례가 필요한 것은 아닙니다. 핵심 기능이 실제로 잘못될 수 있는 경우를 골라 확인합니다.

## 6. 설명 준비

- 화면의 어떤 행동이 어떤 처리 함수로 이어지나요?
- 데이터는 어디에 저장되며 언제 사라지나요?
- 요청이 실패하면 사용자는 무엇을 보나요?
- 가장 중요한 입력 검증은 무엇인가요?
- 지금 구조가 과제 규모에 적절한 이유는 무엇인가요?
