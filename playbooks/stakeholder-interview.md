# 업무 담당자에게 질문하기

목적은 질문 수를 늘리는 것이 아니라, 사용 목적·제약·예외를 알아내어 구현과 검증을 정하는 것입니다.

## 질문 순서

| 알아낼 것 | 질문 예시 | 답을 받은 뒤 할 일 |
|---|---|---|
| 사용자와 결정 | 누가 어떤 상황에서 이 결과를 사용하나요? | 핵심 사용자 흐름 선택 |
| 현재의 문제 | 지금 가장 불편하거나 자주 틀리는 사례 하나를 알려주세요. | 우선 해결할 실패 정의 |
| 입력과 출력 | 실제 입력 예와 원하는 결과 예를 볼 수 있나요? | 입력 형식·출력 기준 확인 |
| 정확성 기준 | 어떤 결과면 잘못됐다고 판단하나요? | 검증 가능한 완료 조건 작성 |
| 예외 | 일부 입력이 잘못됐을 때 어떻게 처리해야 하나요? | 중단·건너뛰기·경고 중 정책 선택 |
| 우선순위 | 제한 시간 안에 반드시 되는 부분은 무엇인가요? | 필수와 선택 기능 분리 |
| 이해 확인 | 목표 A, 필수 흐름 B, 예외 C로 이해했습니다. 맞나요? | 해석의 차이를 구현 전에 수정 |

## 질문 전에 구분할 것

- **이미 적혀 있음:** README를 확인하고 같은 내용을 반복해서 묻지 않습니다.
- **업무 담당자가 아는 사실:** 업무 규칙·우선순위·실제 사례를 질문합니다.
- **구현자가 결정할 사항:** 라이브러리나 내부 구조는 제약에 맞게 직접 판단합니다.
- **아직 확인할 수 없음:** 가정을 명시하고 결과에 미치는 영향을 적습니다.

코딩 AI의 추측은 업무 담당자가 확인한 사실과 다릅니다. 모호한 답을 받으면 구체 사례를 들어 확인합니다.

## 좋은 후속 질문

가상 상황: 담당자가 “최근 매출을 보고 싶다”고 답했습니다.

- 최근은 마지막 데이터 날짜 기준인가요, 현재 날짜 기준인가요?
- 취소·환불은 매출에서 빼나요?
- 판매 시각과 결제 시각 중 어떤 날짜를 기준으로 집계하나요?
- 같은 거래가 두 번 들어오면 무엇으로 중복을 구분하나요?

모든 질문을 일괄적으로 던질 필요는 없습니다. 자료에서 해결되는 항목은 먼저 확인하고, 구현을 바꿀 쟁점만 묻습니다.

## 답을 요구사항으로 바꾸기

~~~text
확인한 사실:
- 담당자의 답을 짧게 기록

구현 결정:
- 그 답 때문에 무엇을 구현하거나 제외했는지

검증 방법:
- 어떤 입력과 기대 결과로 확인할지

남은 불확실성:
- 아직 답을 받지 못한 조건과 임시 가정
~~~

## AI가 나에게 질문하게 하기

본인이 알고 있는 업무 지식을 빠뜨리지 않도록 코딩 AI에 다음처럼 요청할 수 있습니다.

~~~text
내가 제공한 업무 배경을 바탕으로, 구현 방향을 바꿀 수 있는 누락 조건을
중요한 순서대로 최대 5개 질문해주세요. 이미 지시서에 답이 있는 내용은 제외하고,
담당자에게 확인해야 할 사실과 내가 결정할 설계 선택을 구분해주세요.
~~~

답을 모르는 내용은 모른다고 표시합니다. 질문을 받았다고 새로운 업무 사실을 만들어내지는 않습니다.
