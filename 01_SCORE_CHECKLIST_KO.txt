평가 때 좋은 점수를 받기 위해 내가 챙길 것
Cofa 기반 AI 과제 평가 준비 안내


이 문서는 내가 읽고 행동을 점검하기 위한 안내입니다.
공식 채점표가 아니며, 특정 행동의 가점이나 합격을 보장하지 않습니다.
이번 SK하이닉스 2차 예선의 세부 배점과 항목별 비중은 확인되지 않았습니다.
아래의 실천 방법은 공개 평가 설명과 전달받은 안내를 바탕으로 정리한 권장안입니다.


[평가에서 무엇을 보는가?]

Cofa는 결과물뿐 아니라 AI와의 대화, 도구 사용, 검증 기록,
후속 질의응답을 함께 살핀다고 설명합니다.
공개된 평가 관점은 기술·의도·인지입니다. 쉽게 풀면 다음과 같습니다. [1]

기술: 요구한 기능이 제대로 구현됐고 실제로 작동하는가?
의도: 내가 목표와 조건을 정하고 AI의 작업을 적절하게 이끌었는가?
인지: 내가 만든 결과물이 어떻게 동작하고 왜 그렇게 만들었는지 이해하는가?

세 관점은 서로 연결됩니다.
좋은 설명만으로 작동하지 않는 기능이 완성되는 것은 아니며,
기능이 돌아가더라도 선택 이유와 한계를 설명하지 못하면 이해도를 보여주기 어렵습니다.

과거 행사나 공개 예시에 나온 점수 비율을 이번 대회의 배점으로 외우지 마세요.
이 파일의 체크 항목에도 임의의 점수를 붙이지 않았습니다.


[1. 내가 해결하려는 문제를 분명하게 잡기]

좋은 평가를 준비하려면
누가, 어떤 상황에서, 무엇을 하기 위해 결과물을 쓰는지 알아야 합니다.
과제 설명을 먼저 읽고, 구현을 바꿀 수 있는 불명확한 조건만 확인하세요.
업무 담당자와 대화하는 기능이 있는 과제라면 그 기능을 활용하면 됩니다.

예를 들어
“설비 데이터를 보기 좋게 보여주겠다”는 목표만으로는 할 일을 정하기 어렵습니다.
“담당자가 점검할 설비를 고를 수 있도록, 설비별 기준 초과율을 보여주겠다”라면
어떤 입력과 결과가 필요한지 더 분명해집니다.

내가 할 일
- 실제 사용자가 어떤 판단을 하려는지 한 문장으로 적습니다.
- 입력 자료와 원하는 결과를 확인합니다.
- 결과를 바꾸는 업무 기준이 불분명하면 질문합니다.
- 확인한 사실과 아직 확인하지 못한 가정을 구분합니다.

확인할 질문의 예
“측정값이 없는 행도 비율 계산에 포함하나요?”
“기준값과 같은 경우도 초과로 보나요?”
“기간은 측정 시각과 등록 시각 중 무엇을 기준으로 하나요?”

질문 수를 늘리는 것이 목표는 아닙니다.
답을 듣고 실제 계산·화면·우선순위에 반영해야 의미가 있습니다.
처음부터 모든 조건이 주어졌다면 질문을 억지로 만들지 않습니다.

이후 예시는 모두 설명용 가상 과제이며 실제 출제 내용을 뜻하지 않습니다.


[2. 필수 기능과 선택 기능을 나누기]

좋은 평가를 준비하려면
과제에서 반드시 요구한 기능부터 끝까지 완성해야 합니다.
새로운 아이디어를 넣을 때에는 구현 시간뿐 아니라 확인할 시간도 생각하세요.

예를 들어
필수: 제공 파일 읽기, 설비별 계산, 결과 표시, 필요한 오류 안내.
선택: 추가 차트, 색상 변경, 별도 로그인, 새로운 부가 기능.
실제 과제에서 필수로 정했다면 그 항목은 선택 기능으로 빼면 안 됩니다.

내가 할 일
각 필수 기능 옆에 “어떤 결과면 완료인가”를 적습니다.
“표를 만든다”보다 “기간을 바꾸면 그 기간의 수치로 표가 바뀐다”가 확인하기 쉽습니다.
먼저 실제 입력 하나가 최종 결과까지 이어지게 만듭니다.

피해야 할 진행
핵심 계산이 안 되는데 화면 꾸미기부터 하는 것.
선택 기능을 늘리다가 필수 파일이나 제출 문서를 빠뜨리는 것.
여러 기능을 동시에 시작해서 어느 것도 끝까지 동작하지 않는 것.


[3. AI에게 맡길 일을 구체적으로 정하고, 나온 결과를 판단하기]

좋은 평가를 준비하려면
무엇을 맡기는지, 지켜야 할 조건이 무엇인지, 어떻게 확인할지 알려주세요.
AI가 제안한 내용을 받아들일지 결정하는 역할도 내가 맡아야 합니다.

막연한 요청
“좋은 서비스로 전부 만들어 줘.”

범위가 분명한 요청
“제공 CSV에서 설비별 비율을 계산하는 부분부터 만들어 줘.
빈 측정값은 확인한 업무 기준에 따라 처리하고,
작은 예제의 계산 결과와 비교해서 맞는지 확인해 줘.”

내가 할 일
- 이번에 완성할 기능과 유지할 조건을 정합니다.
- 결과를 보고 요구사항과 맞는지 판단합니다.
- 잘못된 부분은 구체적으로 알려 수정하게 합니다.
- 중요한 선택을 바꾸면 이유도 짧게 남깁니다.

예시
“현재 요구에는 로그인 기능이 없고 필수 계산이 남아 있으므로,
로그인은 추가하지 않고 계산과 오류 처리부터 끝내겠습니다.”

이 말은 실제로 그렇게 판단했을 때 남깁니다.
평가에 좋아 보이려고 하지 않은 판단을 기록하면 안 됩니다.

공개 제작자 인터뷰에서도 AI의 과도한 설계를 과제 목적에 맞게 조정하는 능력을
중요하게 설명합니다. 다만 이것이 특정 문장의 가점을 뜻하지는 않습니다. [4]


[4. 실제로 작동하는 결과물을 만들기]

좋은 평가를 준비하려면
파일이나 화면이 존재하는 것뿐 아니라 실제 사용자 흐름이 이어져야 합니다.

웹 화면이라면
내가 직접 필요한 값을 입력하고 버튼을 눌러 결과까지 확인합니다.
값을 바꾸면 결과도 바뀌는지, 잘못 입력하면 안내가 나오는지 봅니다.

데이터 분석이라면
실제 제공 데이터를 읽고, 요구한 기준으로 계산해 결과 파일을 만드는지 봅니다.
열 이름, 날짜, 단위, 중복 처리 때문에 계산이 바뀌지 않는지 확인합니다.

예측 모델이라면
요구된 입력을 받아 올바른 형식의 예측을 만드는지 봅니다.
학습한 데이터와 평가할 데이터가 적절히 나뉘었는지도 확인합니다.

내가 확인할 것
AI가 보여준 예시 화면이나 설명이 아니라 실제 실행 결과인가?
내가 사용할 입력으로도 동작하는가?
처음부터 다시 실행해도 핵심 기능을 사용할 수 있는가?

화면 확인은 대회 내부 Browser에서 내가 직접 합니다.
브라우저 자동 조작을 도입하지 않습니다.


[5. 계산이 맞는지 확인하고, 중요한 실패도 시험하기]

좋은 평가를 준비하려면
정답을 알고 있는 작은 입력과 실제 출력을 비교해야 합니다.
정상적인 입력뿐 아니라 결과를 틀리게 만들 수 있는 경우도 골라 확인하세요.

계산 확인 예시
업무 기준이 “빈 측정값은 제외하고 유효한 측정으로 비율을 계산한다”라고
확인됐다고 가정하겠습니다.

전체 12행 중 2행은 빈 값입니다.
유효한 측정은 10건이고, 그중 기준을 넘은 측정은 2건입니다.
따라서 기대하는 비율은 20%입니다.
실제 프로그램도 20%를 출력하는지 확인합니다.

같이 확인할 중요한 경우
- 자료가 하나도 없을 때
- 필요한 열이 빠졌을 때
- 숫자 자리에 글자가 있을 때
- 기준값과 정확히 같은 값이 있을 때
- 중복 자료가 있을 때
- 필터 결과가 0건일 때

모든 과제에 모든 검사를 만들 필요는 없습니다.
현재 필수 기능을 잘못되게 만들 가능성이 큰 경우부터 확인합니다.

오류가 발견되면
실패를 재현하고 원인을 좁힌 뒤 고칩니다.
처음 실패한 입력과 관련 정상 입력을 다시 확인합니다.

남겨야 할 최소 근거
무엇을 넣었는지 / 기대한 결과 / 실제 결과 / 수정 후 다시 확인한 결과.
“실행됨”과 “계산이 맞음”은 따로 확인해야 합니다.


[6. 선택 이유와 그 선택이 결과에 미친 영향을 남기기]

좋은 평가를 준비하려면
“무엇을 했다”에 더해 “왜 했고, 결과가 어떻게 달라졌는지”를 보여주세요.

설명이 부족한 기록
“빈 값을 제거했습니다.”

판단과 확인이 연결된 기록
“유효한 측정으로만 비율을 계산한다는 업무 기준에 따라 빈 값 2행을 제외했습니다.
12행 중 10행이 계산에 사용됐고, 기준 초과 2건으로 비율 20%를 확인했습니다.”

위 숫자는 설명용입니다. 실제 작업에서는 실제 확인한 수치를 기록해야 합니다.
단순히 빈 값이 있다는 이유로 모든 행을 삭제해서는 안 됩니다.
어떤 열의 빈 값인지와 과제의 계산 기준을 보고 판단합니다.

공식 공개 평가 예시에도 데이터 정리는 구현됐지만,
처리 이유와 전후 결과 비교가 부족해 일부 항목이 충분히 충족되지 않은 사례가 있습니다.
현재 시험의 배점은 아니지만, 구현·이유·검증을 함께 준비할 근거가 됩니다. [3]

내가 할 일
중요한 결정마다 선택, 이유, 확인 결과를 한두 문장으로 남깁니다.
실제로 검토하지 않은 대안이나 측정하지 않은 성능을 만들어 적지 않습니다.
문서가 실제 코드와 다르면 현재 구현에 맞춰 고칩니다.


[7. 시간과 AI 사용을 관리하기]

좋은 평가를 준비하려면
필수 기능, 검증, 설명, 제출에 쓸 시간을 남겨두어야 합니다.
AI가 응답하고 명령을 실행하는 시간도 작업 시간에 포함해 생각하세요.

이번 상세 가이드는 작업 위임과 시간 안배도 AI 활용 역량의 일부로 안내합니다.
운영메일은 AI 사용량과 활용 과정이 평가에 참고될 수 있다고 알렸습니다. [2]

내가 할 일
- 남은 시간을 실제 타이머로 확인합니다.
- 목적 없이 같은 요청을 반복하거나 전체 작업을 계속 다시 만들게 하지 않습니다.
- 필요한 문서와 코드만 읽히고, 기능 단위로 확인합니다.
- 중요한 오류가 남아 있으면 선택 기능을 멈춥니다.
- 마지막에는 저장·제출에 필요한 시간을 확보합니다.

여러 AI 작업을 동시에 맡기고 싶다면
서로 다른 파일이나 독립된 일을 나눌 때 도움이 될 수 있습니다.
같은 파일을 동시에 고쳐 충돌이 생기면 시간이 더 걸릴 수 있습니다.
제공 환경이 지원하고 실제로 도움이 되는 경우에만 사용하세요.

토큰은 AI가 글을 읽고 쓰는 양을 세는 단위입니다.
많이 쓰면 가점, 적게 쓰면 무조건 가점이라는 공식은 확인되지 않았습니다.
사용량을 줄이려고 필요한 검증을 생략하는 것도 권하지 않습니다.


[8. 후속 질문에 내 구현을 기준으로 답하기]

좋은 평가를 준비하려면
내 결과물의 구조, 선택 이유, 확인한 범위와 한계를 이해해야 합니다.
후속 답변이 실제 구현과 맞는지는 Cofa가 확인한다고 설명하는 부분입니다. [1]

과제 수행 중 미리 이해할 것
- 입력이 어디로 들어와 어떤 순서로 처리되는가?
- 핵심 계산이나 판단은 어느 부분에서 이뤄지는가?
- 왜 그 방법을 선택했는가?
- 어떤 입력으로 확인했고 무엇은 확인하지 못했는가?
- 어디에서 실패할 수 있으며, 시간이 더 있으면 무엇을 먼저 확인할 것인가?

좋은 답변의 구조
1. 질문에 대한 결론을 먼저 말합니다.
2. 내 코드나 처리 방식의 구체적인 사실을 설명합니다.
3. 그 선택의 이유와 실제 확인한 근거를 연결합니다.
4. 관련된 한계나 다음 확인 방법을 덧붙입니다.

설명 예시
“빈 값을 0으로 바꾸면 미측정과 정상 측정을 구분할 수 없어서,
확인한 업무 기준에 따라 계산에서 제외했습니다.
12행 중 유효한 10행으로 비율 20%가 나오는지 확인했습니다.
다른 설비의 데이터에서도 같은 누락 패턴이 나타나는지는 아직 확인하지 못했습니다.”

이 예시는 실제로 그 방식으로 구현·확인한 경우에만 성립합니다.
내 코드가 다르게 처리한다면 그 코드에 맞게 답해야 합니다.

약한 설명
“최신 기술이라 선택했습니다.”
“AI가 추천해서 사용했습니다.”
“좋은 구조라서 확장성이 뛰어납니다.”
이 말만으로는 현재 과제에 맞는 이유나 실제 확인한 내용을 알기 어렵습니다.

후속 서술형에서는 AI와 복사·붙여넣기를 사용할 수 없습니다.
이해 점검은 AI가 허용된 과제 수행 시간 안에 글로 진행합니다. [2]


[9. 제출물과 기록을 평가자가 확인할 수 있게 준비하기]

좋은 평가를 준비하려면
요구한 파일이 제자리에 있고 실행 방법이 실제 파일과 맞아야 합니다.
설명 문서의 완료 표시와 실제 구현·검증 상태도 일치해야 합니다.

내가 할 일
- 과제에서 지정한 파일명과 저장 위치를 확인합니다.
- 필요한 입력과 실행 방법을 짧게 정리합니다.
- 필수 조건별로 완료, 미확인, 미완료를 구분합니다.
- 필요한 출처와 사용한 부분을 기록합니다.
- 실제 제출 화면의 안내에 따라 제출하고 완료 상태를 확인합니다.

계획 문서나 협업 기록은 AI의 도움으로 작성할 수 있다고 안내돼 있습니다.
다만 판단 근거, 검증 결과, 한계가 실제 작업과 맞는지는 내가 확인해야 합니다. [2]

긴 보고서나 많은 파일이 그 자체로 좋은 평가를 보장하지 않습니다.
이미 자동으로 수집되는 작업 기록도 있으므로,
보여주기 위한 기록을 대량으로 만들기보다 중요한 판단과 실제 결과를 명확히 남기세요.


[점수와 관련해 오해하지 말 것]

“프롬프트를 길게 쓰면 점수가 높다.”
길이 자체의 가점은 확인되지 않았습니다.
목표, 조건, 확인 방법이 분명한지가 더 유용한 점검 기준입니다.

“질문을 많이 하면 무조건 유리하다.”
필요한 조건을 확인하고 구현에 반영하는 것이 목적입니다.
이미 답이 있는 질문을 반복할 필요는 없습니다.

“Skill이나 MCP를 많이 쓰면 가점이다.”
사용 개수 자체의 가점은 확인되지 않았습니다.
현재 문제를 해결하는 데 실제 도움이 되는 자료와 도구를 사용하세요.

“테스트를 많이 만들면 충분하다.”
개수보다 필수 기능과 중요한 실패를 실제로 확인했는지가 중요합니다.
현재 코드의 출력을 그대로 정답으로 놓은 검사는 오류를 놓칠 수 있습니다.

“문서에 검증했다고 쓰면 된다.”
실제 입력·출력·실행 기록과 맞아야 합니다.
AI가 문제없다고 답한 것만으로 실행 검증이 된 것은 아닙니다.

“한계를 적으면 무조건 감점이므로 숨기는 편이 낫다.”
한계를 적으면 자동 가점이라는 뜻도 아닙니다.
먼저 중요한 문제를 해결하고, 남은 문제는 실제 영향과 함께 정확히 설명하세요.


[시간이 모자랄 때의 수정 우선순위]

1. 실행이나 제출을 막는 문제
2. 누락된 필수 기능
3. 잘못된 수치·잘못된 결과를 만드는 오류
4. 중요한 실패 상황과 검증 부족
5. 실행 설명과 내 이해의 부족
6. 선택 기능과 화면 다듬기

위 순서는 준비를 위한 권장안입니다.
실제 과제에서 화면 품질이나 특정 성능을 필수로 요구하면 그 요구를 함께 반영하세요.


[제출 전 내가 확인할 10가지]

[ ] 해결할 문제와 사용자를 한 문장으로 설명할 수 있다.
[ ] 필수 기능과 제출 조건을 빠뜨리지 않았다.
[ ] 실제 입력 하나가 최종 결과까지 이어진다.
[ ] 핵심 계산을 정답이 있는 작은 입력과 비교했다.
[ ] 중요한 오류·빈 입력·경계 상황을 골라 확인했다.
[ ] 발견한 오류를 고친 뒤 같은 입력으로 다시 확인했다.
[ ] 중요한 선택의 이유와 결과 영향을 설명할 수 있다.
[ ] 문서의 완료·검증 내용이 실제 코드와 일치한다.
[ ] 확인하지 못한 부분과 남은 한계를 구분할 수 있다.
[ ] 필수 파일·실행 방법·저장 상태를 확인하고 제출할 시간이 남아 있다.

이 체크리스트는 점수 예측표가 아닙니다.
해당하지 않는 항목은 과제에 맞게 바꾸고, 실제로 확인한 항목만 표시하세요.


[규정은 별도로 지키기]

좋은 결과물과 별개로 규정 위반이 확인되면 평가에서 불이익을 받을 수 있습니다.
제공된 AI와 허용된 자료를 사용하고, 공개 저장소는 안내된 기간까지 공개로 유지합니다.
문제·데이터·작성 답안·작업 기록을 외부 서비스나 GitHub로 보내지 않습니다.
Codex 업데이트, 감독·업로드 제한 우회, Computer Use는 하지 않습니다.
후속 서술형에서는 AI를 사용하지 않습니다.
세부 조건은 실제 과제 지시와 공식 운영 안내를 따릅니다.
