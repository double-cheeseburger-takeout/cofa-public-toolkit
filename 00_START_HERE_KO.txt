대회 중 내가 보는 툴킷 사용 안내
처음 시작할 때부터 제출할 때까지


이 파일은 내가 읽고 따라가는 안내문입니다.
각 단계에 적힌 '참고 파일'은 필요할 때 Codex에게 읽혀 사용하면 됩니다.
내가 툴킷 안의 모든 문서를 공부하거나 파일 이름을 외울 필요는 없습니다.


[먼저, 내가 받은 폴더는 무엇인가?]

툴킷에는 과제를 계획하는 방법, 코드를 만들 때의 확인 사항,
오류를 찾는 방법, 제출 전 점검 방법이 들어 있습니다.
현재 시험의 정답이나 완성된 앱이 들어 있는 것은 아닙니다.

예를 들어 “CSV를 분석해 결과를 보여주는 화면을 만들라”는 과제라면,
툴킷은 무엇부터 만들고, 계산이 맞는지 어떻게 확인할지 도와줍니다.
실제 화면과 계산 코드는 그 과제의 요구에 맞춰 만들어야 합니다.

Skill은 'AI가 특정 작업을 할 때 참고하는 절차 문서'입니다.
다운로드만으로 자동 실행되는 기능은 아닙니다.
“이 파일을 읽고 지금 작업에 적용해 줘”라고 말하면 됩니다.

아래 참고 파일은 모두 받은 cofa-public-toolkit 폴더 안에 있습니다.
예: skills/task-plan/SKILL.md
→ skills 폴더 안의 task-plan 폴더에 있는 SKILL.md라는 문서입니다.

Clone을 마쳤다면 아래 1단계부터 보시면 됩니다.


[1. 문제를 처음 받았을 때 — 무엇을 만들어야 하는지 정하기]

지금 할 일
먼저 실제 과제 설명을 읽습니다. 그다음 Codex가 과제와 제공 파일을
읽고 “무엇을 만들고, 무엇을 제출해야 하는지” 짧게 정리하게 합니다.

내가 확인할 것
- 해결해야 하는 문제가 무엇인지
- 반드시 되는 기능이 무엇인지
- 제출해야 하는 파일이나 문서가 무엇인지
- 설명이 불분명해서 먼저 확인할 조건이 있는지

예를 들어 매출 분석 과제라면, 환불을 빼는지와 기간을 어떻게 잡는지에
따라 결과가 달라질 수 있습니다. 이런 조건을 먼저 확인하는 것입니다.
이미 과제 설명에 답이 있는 내용은 다시 물을 필요가 없습니다.

이때 참고할 파일
- AGENTS.md: 작업할 때 지킬 공통 원칙
- skills/task-plan/SKILL.md: 필수 기능과 진행 순서를 정리하는 방법

처음 Codex에 할 말
“_reference/cofa-public-toolkit에 받은 자료가 있어.
실제 과제 지침을 먼저 읽고, 그 폴더의 RULES.md와 AGENTS.md,
계획용 Skill을 참고해서 필수 기능과 제출 조건부터 정리해 줘.”

다음으로 넘어가도 되는 때
내가 “무엇을 만들면 이 과제를 완료한 것인지” 설명할 수 있을 때입니다.
계획 문서를 길게 만드는 것보다 필수 기능을 분명히 하는 것이 중요합니다.


[2. 과제 종류를 알았을 때 — 맞는 안내서 하나 고르기]

지금 할 일
현재 과제가 데이터 분석인지, 웹 화면인지, 예측 모델인지 보고
관련된 안내서만 사용합니다. 아래 세 문서를 모두 읽힐 필요는 없습니다.

표·CSV·집계 과제라면
playbooks/data-analysis.md
빈 값, 중복, 날짜, 단위, 합계 계산을 어떻게 확인할지 알려줍니다.
예: 빈칸을 전부 0으로 바꿔도 되는지, 같은 행이 두 번 들어왔는지 확인합니다.

웹 화면·서버 과제라면
playbooks/web-and-api.md
입력한 값이 처리되어 결과 화면까지 이어지는지 확인하는 방법입니다.
예: 조회 버튼을 눌렀을 때 결과가 나오는지, 잘못 입력하면 안내가 나오는지 봅니다.

예측·분류 모델 과제라면
playbooks/machine-learning.md
학습용 데이터와 평가용 데이터가 제대로 나뉘었는지,
성능을 올바른 기준으로 계산했는지 확인하는 방법입니다.

Codex에는 이렇게 말하면 됩니다
“툴킷에서 지금 과제에 맞는 안내서를 참고해서, 기존 도구로 만들 방법을 정해 줘.”

내가 확인할 것
선택한 방법으로 필수 기능을 만들 수 있는지 확인합니다.
기존 프로젝트가 있는데 이유 없이 다른 기술로 전부 다시 만들고 있다면,
왜 바꿔야 하는지 설명을 듣고 필요한 변경인지 판단합니다.


[3. 기능을 만들 때 — 가장 중요한 일 하나부터 끝까지]

지금 할 일
가장 중요한 기능 하나를 먼저 만들게 합니다.
매출 분석 예시라면 “CSV 읽기 → 합계 계산 → 결과 표시”가 한 흐름입니다.
이 흐름이 실제로 되는 것을 확인한 뒤 다음 필수 기능을 추가합니다.

이때 참고할 파일
prompts/implement.md
AI에게 이번에 만들 기능과 완료 조건을 구체적으로 전달하는 요청문입니다.

Codex에는 이렇게 말하면 됩니다
“구현 요청문을 참고해서 가장 중요한 기능 하나부터 끝까지 만들고,
실제 입력을 넣어 결과가 나오는지 확인해 줘.”

내가 확인할 것
AI의 “만들었습니다”라는 보고만 보지 말고 실제 결과를 봅니다.
화면 과제라면 내가 직접 입력하고 버튼을 눌러봅니다.
분석 과제라면 결과 표나 수치가 실제로 생성됐는지 확인합니다.

웹 화면을 어디서 보나?
대회 안의 Browser에서 봅니다.
Codex에게 “내가 볼 포트와 경로, 눌러볼 버튼을 알려줘”라고 하면 됩니다.

포트는 서비스에 연결할 때 쓰는 번호이고, 경로는 서비스 안의 페이지 위치입니다.
'/'는 기본 페이지입니다. 실제 포트는 실행 결과를 보고 안내받으세요.
서버를 켜 둔 터미널을 닫으면 화면 연결이 끊길 수 있습니다.

다음으로 넘어가도 되는 때
실제 입력 하나가 끝까지 처리되고, 필요한 결과를 확인했을 때입니다.


[4. 기능이 만들어졌을 때 — 결과가 맞는지 확인하기]

지금 할 일
기능을 만들거나 계산 방법을 바꿀 때마다 실제 결과를 확인합니다.
이것이 검증입니다. 마지막 제출 직전에만 하는 일이 아닙니다.

이때 참고할 파일
skills/verify-result/SKILL.md
기대하는 정답과 실제 출력이 일치하는지 확인하는 절차입니다.

Codex에는 이렇게 말하면 됩니다
“검증용 Skill을 참고해서, 정답을 계산할 수 있는 작은 입력과
잘못된 입력으로 지금 기능을 실제로 확인해 줘.”

예를 들어 무엇을 확인하나?
세 숫자를 더하는 기능이라면 100, 200, -50을 넣었을 때 250이 나오는지 봅니다.
파일을 읽는 기능이라면 필요한 열이 없는 파일에서 어떻게 동작하는지 봅니다.
검색 화면이라면 결과가 없는 검색어를 넣었을 때 무엇이 표시되는지 봅니다.
실제 과제에 필요한 사례를 골라 확인하면 됩니다.

내가 확인할 것
- 무엇을 넣었는가?
- 원래 어떤 결과가 나와야 하는가?
- 실제로 무엇이 나왔는가?
- 아직 확인하지 못한 부분은 무엇인가?

결과가 다르면 아래 '오류가 반복될 때' 부분을 사용합니다.
수정한 뒤에는 처음 실패했던 입력을 다시 확인해야 합니다.


[5. 어느 정도 완성됐을 때 — 내가 설명할 수 있는지 확인하기]

지금 할 일
내가 만든 결과물의 핵심 흐름과 선택 이유를 이해합니다.
AI가 작성한 코드라도 어떤 일을 하는지는 내가 알아야 합니다.

이때 참고할 파일
skills/explain-work/SKILL.md
실제 구현을 바탕으로 질문을 받고 이해가 부족한 부분을 찾는 절차입니다.

Codex에는 이렇게 말하면 됩니다
“내 구현의 입력부터 결과까지 쉽게 설명하고,
선택 이유와 검증 내용에 대해 한 번에 하나씩 질문해 줘.”

내가 답해볼 질문
- 입력 데이터가 들어오면 어떤 순서로 처리되는가?
- 왜 이 계산 방법이나 구조를 골랐는가?
- 제대로 동작하는지 어떤 입력으로 확인했는가?
- 아직 해결하지 못한 문제는 무엇인가?

모르는 부분이 나오면 실제 코드를 기준으로 다시 설명을 들으면 됩니다.
하지 않은 검증이나 생각하지 않았던 이유를 만들어 외우는 것은 도움이 되지 않습니다.

언제 해야 하나?
AI 사용이 허용된 과제 수행 시간 안에 합니다.
소리 내어 말하지 않고 제공된 Codex 채팅에 글로 답합니다.
후속 서술형이 시작되면 AI와 복사·붙여넣기를 사용하지 않고 직접 답해야 합니다.


[6. 제출 시간이 가까워졌을 때 — 제출할 수 있는 상태인지 확인하기]

지금 할 일
마지막 15분 정도는 저장과 제출 확인에 남겨둡니다.
새 기능을 늘리기보다 필수 기능의 오류와 빠진 파일을 확인합니다.
상황에 따라 더 일찍 제출 준비를 시작해도 됩니다.

이때 참고할 파일
skills/prepare-submission/SKILL.md
실제 과제의 제출 조건과 현재 파일·실행 상태를 대조하는 절차입니다.

Codex에는 이렇게 말하면 됩니다
“제출 준비용 Skill을 참고해서 필수 파일, 저장 위치, 실행 방법과
미완료 사항을 확인하고, 내가 마지막으로 할 일을 알려 줘.”

내가 직접 확인할 것
- 과제에서 요구한 파일이 정해진 이름과 위치에 있는가?
- 수정한 내용이 저장됐는가?
- 설명한 방법으로 실제 실행되는가?
- 필수 기능 중 안 되는 것이 남아 있는가?

화면에서 제출하는 순서
1. '제출하고 문제풀기'를 눌러 미리보기를 확인합니다.
2. 고칠 것이 있으면 미리보기를 닫고 수정합니다.
3. 준비가 끝나면 '제출물 확정하고 문제풀기'를 누릅니다.
4. 후속 서술형에 직접 답합니다.
5. 마지막 답안을 제출하고 처리·녹화 업로드가 끝날 때까지 기다립니다.
6. 최종 제출 완료 화면과 제출 정보를 확인한 뒤 브라우저를 닫습니다.

반드시 알아둘 점
제출물을 확정하면 파일을 수정할 수 없다고 안내돼 있습니다.
미리보기에는 일부 파일만 보이므로, 보이는 것만 제출된다고 생각하면 안 됩니다.
_reference 폴더가 제출에서 자동 제외되는지도 확인된 바 없습니다.
파일을 선택하거나 제외할 수 있는지는 내부 Cofa Helper에 사용법을 물어보세요.
제출은 시험 화면에서 합니다. GitHub로 파일을 보내는 방식이 아닙니다.


[진행 중 이런 상황이 생기면]

오류가 계속 반복된다
참고: playbooks/debugging.md
내가 한 행동, 기대한 결과, 실제 결과를 구체적으로 알려주세요.
“조회 버튼을 눌렀는데 표가 비어 있다”처럼 설명하면 됩니다.
Codex에는 “오류를 재현해서 원인부터 확인하고, 고친 뒤 다시 확인해 줘”라고 말합니다.

빠뜨린 요구사항이 없는지 전체를 보고 싶다
참고: skills/review-changes/SKILL.md
“필수 기능 누락과 잘못된 결과를 만드는 경우를 근거와 함께 찾아 줘”라고 합니다.
지적이 나오면 실제 문제가 확인됐는지 보고 중요한 것부터 고칩니다.

대화가 길어져 새 대화에서 이어가야 한다
참고: skills/handoff-task/SKILL.md
지금까지 한 일, 중요한 결정, 실행 방법, 남은 문제를 짧게 정리하게 합니다.
새 대화에서는 그 메모와 실제 과제 지침을 읽힌 뒤 이어갑니다.
인수인계란 다음 대화가 현재 작업을 이어갈 수 있도록 상태를 남기는 것입니다.

추가 자료가 필요하다
참고: external-resources/CATALOG.md
여기에는 외부 자료의 링크와 활용법이 있습니다. 모두 설치된 것은 아닙니다.
“현재 막힌 부분에 필요한 자료만 골라 참고해 줘”라고 요청하면 됩니다.


[작업 기록은 무엇을 남기면 되나?]

templates/WORKLOG.md는 빈 작업 기록 양식입니다.
실제 작업 공간에 기록 하나를 만들고 다음 내용만 짧게 남기면 됩니다.

- 무엇을 만들었는지
- 중요한 방법을 왜 선택했는지
- 무엇을 실제로 확인했고 결과가 어땠는지
- 아직 안 되거나 확인하지 못한 것은 무엇인지

대화가 길어졌을 때와 제출 전에 현재 상태를 확인하는 데 도움이 됩니다.
Codex가 기록하게 하되, 내용이 실제 작업과 맞는지는 내가 확인합니다.
target.txt를 같은 용도로 쓰고 있다면 두 파일에 똑같이 적을 필요는 없습니다.
시험 내용으로 채운 기록은 시험 작업 공간 안에 두고 GitHub에는 올리지 않습니다.


[Python 도구는 꼭 실행해야 하나?]

필요할 때만 사용하면 됩니다. 사용법은 scripts/README.md에 있습니다.

csv_profile.py
CSV에 빈 값이나 중복이 있는지 처음 살펴볼 때 도움이 됩니다.
빈칸을 지울지, 0으로 바꿀지 같은 판단까지 대신하지는 않습니다.

run_checks.py
내 과제에 맞는 검사 명령을 여러 개 실행하고 결과를 기록할 때 씁니다.
어떤 검사를 할지는 실제 과제에 맞춰 정해야 합니다.

check_deliverables.py
필수 파일이 있는지, 비어 있지는 않은지 확인할 때 씁니다.
파일 내용이 정답인지까지 확인하는 도구는 아닙니다.

명령어를 외울 필요는 없습니다.
“scripts 사용법을 보고 지금 필요한 도구만 실제 과제에 맞게 써 줘”라고 하면 됩니다.
examples와 tests는 툴킷 연습·자체 확인용이므로 시험에서 전부 실행할 필요는 없습니다.


[시간이 부족하면 무엇부터 해야 하나?]

먼저 실행이나 제출을 막는 문제를 해결합니다.
그다음 빠진 필수 기능과 잘못된 결과를 고칩니다.
선택 기능이나 화면 꾸미기는 그 뒤에 판단합니다.

180분 과제의 권장 배분 예시입니다.
- 처음 25분: 문제 이해와 필수 범위 결정
- 다음 95분: 구현과 기능별 확인
- 다음 25분: 전체 검증과 중요한 오류 수정
- 다음 20분: 재실행, 설명 정리, 본인 이해 확인
- 마지막 15분: 저장과 제출 확인

남은 시간은 실제 타이머를 보고 Codex에게 알려주세요.

[규정 때문에 헷갈릴 때]

외부의 완성 답안으로 결과물을 통째로 대체하는 행위는 금지됩니다.

시험 중에는 제공된 Codex와 허용된 작업 환경 안에서 자료를 이용합니다.
외부 ChatGPT나 GitHub 탭으로 이동하지 않습니다.
문제·데이터·코드·작업 기록을 밖으로 보내거나 Git Push하지 않습니다.
